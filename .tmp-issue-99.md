TITLE: Introduce UI-agnostic branding tokens and feature flags

## Epic

#73 Replaceable UI and Branding

## User story

As a product owner, I want colors, typography, logos, spacing, terminology, and feature flags in UI-agnostic configuration so the Next.js presentation (and any future UI adapters) share one brand source of truth.

## Rationale

Explicit branding/configurability requirement.

**Context update:** Streamlit has been retired as an interactive presentation surface (#228, ADR 0004). Next.js (`web/`) plus FastAPI under `presentation/http/` is the sole supported interactive UI. Branding tokens and feature flags must target that stack — not Streamlit.

## Exact scope

- Design tokens/config module consumed by presentation (Next.js / HTTP)
- Feature flags for Sprint 2 capabilities (RAG, tools, etc.)
- **Independent feature flags** for optional domain packs and connectors (in addition to capability flags)
- Default terminology and navigation remain **neutral**; Story/QA labels appear only through enabled Software Delivery pack presentation configuration

## Exclusions

- Building a full design system component library
- Implementing a full Next.js theme system beyond consuming tokens
- Moving pack/connector semantics into shared branding defaults
- Any Streamlit or dual-stack branding work (retired)

## Acceptance criteria

- Given branding config, when Next.js (or presentation config consumers) reads it, then primary terminology/colors/logo paths come from tokens
- Given default (pack-disabled) configuration, when UI boots, then terminology/navigation stay neutral and do not require Story/QA labels
- Given an optional pack or connector flag disabled, when UI/core boots, then the gated affordance is hidden/disabled and core startup, upload, retrieval, and generic chat still work
- Given domain/application, when scanned, then they do not hardcode UI-framework theme APIs (e.g. former Streamlit theme APIs)

## Technical notes

- JSON/YAML/TOML/python constants acceptable
- Align with composition settings such as `PROMPT_PACKS` / `DOMAIN_TOOL_PACKS` without inventing pack imports in presentation
