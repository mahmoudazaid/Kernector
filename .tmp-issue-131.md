TITLE: Replace JSON document catalog with a transactional SQL adapter

## Context

Ticket #122 introduced `DocumentCatalog` with `JsonDocumentCatalog` as the smallest durable registry for the current single-user Streamlit application. JSON is intentionally temporary: it does not provide database transactions, safe multi-process writes, migrations, or suitable concurrency for the planned Next.js/multi-user direction.

This issue is a **follow-up to #122**. Implementation must not begin until an approved **project/workspace/authorization** model exists. **Do not modify code in this task** — tracking and planning only.

## Goal

Add a transactional SQL-backed `DocumentCatalog` adapter without changing application use cases or presentation code.

## Scope

* Implement `SqlDocumentCatalog` behind the existing `DocumentCatalog` port.
* Prefer SQLite initially unless the project’s deployment design requires PostgreSQL.
* Persist every `CatalogDocument` field with uniqueness that includes the **resolved scope identity** from the approved workspace/authorization model (for example project/workspace id plus source identity). Do **not** assume `(source_type, source_id)` is globally unique or safe across workspaces.
* Make `get`, `all`, `upsert`, and `delete` transactional.
* Add schema creation and explicit versioned migrations that encode the resolved scope identity.
* Provide a one-time, idempotent migration from `data/catalog/uploads.json` into the scoped schema.
* Preserve `JsonDocumentCatalog` for local/lightweight usage.
* Select the adapter through configuration; do not branch inside application or presentation.
* Cover restart persistence, duplicate identities within a scope, rollback, concurrent writes, migration success, and migration failure.
* Document when JSON versus SQL should be selected.

## Out of scope

Changes to Chroma retrieval, document chunking, embedding, Next.js UI implementation, and replacing the `DocumentCatalog` port.

**Clarification on tenancy:** designing the project/workspace/authorization model is owned by the future **Project Workspaces and Authorization** epic (issue TBD). This ticket consumes that approved model for schema uniqueness and filters; it does not invent a parallel tenancy design.

## Acceptance criteria

1. Application and presentation work unchanged with either catalog adapter.
2. SQL enforces unique document identity **within the resolved workspace/project scope**.
3. Failed writes roll back without partial catalog state.
4. Concurrent writers do not lose updates.
5. Existing JSON rows can be migrated without changing their statuses, timestamps, or chunk counts, mapping into the scoped identity model.
6. Re-running the migration creates no duplicates.
7. Migration failure leaves the source JSON and SQL catalog recoverable.
8. Offline tests and `uv run pytest -q` pass.
9. Documentation explains configuration, migration, rollback, adapter selection, and the scoped uniqueness rule.
10. Implementation remains blocked until the workspace/authorization model is approved and referenced here.

## Dependencies

* **Blocked by #122** — requires the JSON catalog port and adapter delivered there (closed).
* **Blocked by approved project/workspace/authorization model** — future **Project Workspaces and Authorization** epic (issue TBD). Do not start SQL schema work against a global `(source_type, source_id)` uniqueness assumption.
* Related presentation track: EPIC #124 (multi-user/Next.js timing), but authorization scope is the hard gate for uniqueness/migrations.
