# ADR 0011: Project Intelligence foundation — project identity, relationships, and storage

## Status

Proposed

## Context

[#331], [#337] and [#344] scope their data by `workspace_id + project_id`, but
[ADR 0006](0006-workspace-scope-identity.md) defines only `workspace_id` and
explicitly defers "an approved project/workspace/authorization model". No
decision says what a project is, which sources belong to it, or how artifacts
from different sources relate to each other.

Without one shared decision, each Project Intelligence slice ([#369]) would
invent its own tables, might add a graph database, or would push Software
Delivery vocabulary (stories, tests, APIs) into the generic core.
[EPIC #68] and [ADR 0001](0001-domain-agnostic-knowledge-foundation.md) forbid
that: business vocabulary lives in packs, and the core stays domain-agnostic.

[#331] is separately blocked on its own memory ADR (ownership, approval,
retention). This ADR does not duplicate it. It records only the shared
`project_id`, the relationship side, and the boundaries between the three.

Reusable parts that already exist:

- Persistence: stdlib `sqlite3` with numbered SQL migrations applied by
  `apply_migrations` in `infrastructure/catalog/sql_schema.py`, the
  `catalog_documents` table, and `versioned_workspace_records` with
  compare-and-swap in `infrastructure/workspace_store/`.
- Identity: `SourceReference(source_id, source_type)`,
  `ConnectorDocument.revision`, and `connector_id` on catalog rows.
- Open vocabulary precedent: `SourceType` documents well-known values but is
  not a closed validation set.
- Exposure: the shared MCP tool registry with human approval
  ([ADR 0010](0010-mcp-side-effect-tools-shared-registry-hitl.md)) and the
  versioned HTTP API.

ADR number `0007` is already used twice. This ADR takes the next free number
and does not renumber existing ADRs.

## Decision

### 1. Project identity

- A **project** is identified by `project_id`, an opaque, stable identifier
  scoped to one workspace. The full key is always `workspace_id + project_id`.
- `project_id` follows the ADR 0006 identifier shape: case-sensitive,
  `fullmatch`es `[A-Za-z0-9_-]+`, at most 64 characters. It is generated by
  Kernector (for example `prj_7f3a…`), never derived from a name, a provider
  key, or a source, and never reused after deletion.
- A project also has a **display name** and a **slug**. Both may change. The
  slug is unique within the workspace. Nothing references a project by name or
  slug; references always use `project_id`.
- There is **no reserved default project** and no implicit fallback. Data that
  needs a project and has none is reported as unassociated, not assigned
  somewhere.
- A connector or source **never implies a project**. A source belongs to a
  project only through an explicit, confirmed association (decision 2).
- `workspace_id` is always bound as a query parameter, as ADR 0006 requires.
  Project rows in one workspace are never visible from another.

### 2. Source association

An **association** links a project to part of a connected source:

```text
(project_id, connector_id, scope_kind, scope_value) + context roles + optional component
```

- **Many-to-many.** A project can have many associations, and the same scope
  can be associated with several projects. Each pair is its own association.
- **Provider-neutral scope.** `scope_kind` and `scope_value` are opaque tokens.
  Examples: `project_key=OIE` (Jira), `repo=acme/oie-orders` (GitHub),
  `folder=1AbC…` (Drive). The connector that owns `connector_id` validates its
  own scope kinds; the core only checks shape.
- **Context roles.** Zero or more registered context tokens (decision 10). A
  role is the default context for that scope's artifacts. Zero roles is valid
  only when no context vocabulary is registered.
- **Component.** An association may belong to a component (decision 11).
- **Confirmation.** An association is `suggested`, `confirmed` or `rejected`.
  Only `confirmed` associations scope retrieval, classification or
  relationships. Only an operator confirms or rejects. Nothing confirms
  automatically.
- **Suggestions.** Connectors or packs may suggest associations, for example
  from the project keys in a Jira grant or the repositories in a GitHub sync
  configuration. A suggestion is never treated as a fact. A `rejected`
  association is kept so the same suggestion is not repeated.
- **Conflicts.** If a suggestion contradicts a confirmed or rejected
  association, for example by assigning different roles to the same scope in
  the same project, Kernector shows both to the operator and changes nothing
  until the operator chooses.

### 3. Artifacts and token contracts

- An **artifact** is a catalog document plus an `ArtifactDescriptor`:
  - `kind`: an opaque token such as `issue`, `test_case`, `api_spec`,
    `source_file` or `adr`.
  - `external_keys`: identifiers by which other artifacts can refer to it, for
    example `jira_key=OIE-123`, `path=services/orders/openapi.yaml`, or
    `operation_id=createOrder`.
  - `revision`: the `ConnectorDocument.revision` the descriptor was derived
    from.
- **Identity reuses `SourceReference`.** There is no new document model and no
  second identifier. An artifact is the catalog row
  `(workspace_id, source_type, source_id)` with its descriptor.
- **Project membership is derived.** An artifact belongs to every project with
  a confirmed association whose scope covers its source. Membership is not
  copied onto the descriptor.
- **Opaque validated tokens.** Artifact kinds, relation types, context tokens,
  evidence-role tokens, assertion labels and purpose names are all opaque
  tokens. The core checks only their shape and whether a pack registered them.
- **Meaning lives in packs.** Packs register each token's meaning, the allowed
  context pairs, classification rules and purpose-selection policies as data,
  following the `SourceType` precedent. The core hardcodes no kind, relation,
  context, role or purpose literal. The well-known values in this ADR are
  documented here and defined in the pack.

### 4. Relationships

A relationship is a directed edge `(subject, relation_type, object)`. Both ends
are `SourceReference`s of artifacts in the same workspace. Each edge carries
three independent axes. None is derived from another.

**Origin tier** — how the edge was produced. Fixed when the edge is created.

| Origin | Meaning |
|---|---|
| `provider_declared` | The source system declares the link explicitly, for example Jira `issuelinks`. |
| `deterministic` | A documented rule matched an identifier, for example a test file that cites `OIE-123`. |
| `inferred` | A model proposed the edge. |
| `human_confirmed` | A person asserted the edge directly. |

**Verification state** — whether the edge may be used as evidence.

| State | Meaning |
|---|---|
| `unverified` | Proposed, not yet confirmed. Shown only as a labelled candidate. |
| `verified` | May be used as evidence. |
| `rejected` | A person rejected it. Never shown as evidence. Kept so the same proposal is not repeated. |

Transitions:

- `provider_declared`, `deterministic` and `human_confirmed` edges start as
  `verified`.
- `inferred` edges start as `unverified`.
- `unverified → verified` happens only through an explicit human confirmation.
  `unverified → rejected` happens only through an explicit human rejection. A
  person may also reverse a decision (`verified ↔ rejected`).
- **No automatic process promotes an inferred edge.** Not confidence, not
  repetition, not agreement between models. A confirmation records who
  confirmed and when, and the edge keeps its original `inferred` origin.

**Freshness** — whether the evidence still matches the source. Driven by sync,
independent of verification.

| Freshness | Meaning |
|---|---|
| `current` | Every evidence revision matches the latest successful sync of its source. |
| `stale` | The source changed and the edge has not been re-derived yet. |
| `removed` | The source, or the link inside it, is gone. Kept for audit and excluded from retrieval. |

**Confidence** — a number from 0 to 1, used only for ranking. Provider-declared,
deterministic and human-confirmed edges have confidence 1.

**Evidence references** — one or more per edge. Each holds:

- the evidence source `SourceReference`;
- the source `revision` the evidence was read from;
- a `locator` or `span`, for example `field=issuelinks`, or a path with a line
  range;
- exactly one producer id: `rule_id` for `deterministic` edges, `model_run_id`
  for `inferred` edges, or the confirming actor for `human_confirmed` edges.
  `provider_declared` evidence needs no producer id because the locator names
  the provider field.

### 5. Storage

Relationship, project, association, component and descriptor data live in
**relational tables in the existing SQLite catalog database**, added through
the numbered migration runner. Every row carries `workspace_id`.
Operator-edited records (projects, associations, components, confirmations)
use compare-and-swap, following `versioned_workspace_records`. The alternatives
and the revisit triggers are recorded under
[Rejected alternatives](#rejected-alternatives). Exact table design belongs to
the implementing tickets ([#372]–[#376]).

### 6. Reconciliation

Reconciliation runs from **per-source sync outcomes**. It is incremental and
invalidates instead of rebuilding.

- **Successful sync.** For each document whose revision changed, re-derive its
  descriptor and every edge whose evidence cites it. Edges whose evidence still
  holds return to `current` with the new revision. Edges whose evidence no
  longer holds become `removed`. Documents with unchanged revisions are not
  touched.
- **Deleted documents.** Every edge whose subject, object or evidence is the
  deleted document becomes `removed`.
- **Between change detection and re-derivation,** affected edges are `stale`.
- **Failed or partial sync.** Freshness does not change for scopes that did not
  sync. The last successful sync time and the failure are reported (decision
  12).
- **Verification survives reconciliation.** A stale human confirmation stays
  `verified` but is shown as stale. A re-derived inferred proposal never
  overrides a `rejected` state.
- There is no full rebuild in normal operation. A full re-derivation is an
  explicit operator action.

### 7. Retrieval and context

- **Project-scoped filtering.** Every query is scoped to one
  `workspace_id + project_id`, and optionally to one component.
- **Exact identifier lookup.** `external_keys` support exact lookup, for
  example `OIE-123`, before any semantic search.
- **Bounded traversal.** At most 2 hops from the seed artifacts. A consumer
  may ask for fewer.
- **Ranking.** Verified before unverified, current before stale, and then
  confidence. `rejected` and `removed` edges are never returned as evidence.
- **Token budgeting.** The assembler fits the bundle into the consumer's budget
  and reports what it left out.
- **Context is ephemeral.** A context bundle is computed for one request and
  never persisted. On-demand resolution over persisted edges happens here.

### 8. Boundaries

- **Project Memory ([#331], exposed through [#337]).** Memory holds
  **approved decisions only**, governed by #331's own ADR. Relationships may
  **propose** memory candidates but never approve them. Approved decisions are
  not a context (decision 10); they appear in their own bundle section.
- **Project History ([#344]).** History holds change events and evidence
  snapshots. Relationships are **current state only**. Past relationship
  states are not history; `removed` edges are kept only for audit.
- **Workspaces and authorization ([EPIC #257]).** Project scoping does not make
  Kernector multi-tenant-safe. Vector-store workspace scoping remains a #257
  prerequisite for any multi-workspace claim.
- **Generic Knowledge Foundation ([EPIC #68]).** The core stays
  domain-agnostic. Software Delivery meaning lives only in
  `packs/software_delivery`.

### 9. Layering and import rules

These rules follow the layer table in [ARCHITECTURE.md](../../ARCHITECTURE.md)
and [ADR 0008](0008-group-modules-by-concern.md). Nothing here relaxes them.

- **`domain/`** — Project Intelligence contracts (`project_id`,
  `ArtifactDescriptor`, relationship, evidence, outcome) and ports. Imports the
  standard library only. Contains no context, relation, kind, purpose or role
  literals.
- **`application/`** — use cases such as associate, classify, reconcile and
  assemble. Imports `domain` only and reaches storage only through `domain`
  ports.
- **`infrastructure/`** — SQLite adapters, using the existing numbered
  migrations, and connector extractors that produce descriptors and
  provider-declared edges. Imports `domain` and approved libraries only. Never
  imports `application`, `composition`, `presentation` or `packs`.
- **`packs/software_delivery`** — context vocabulary, classification rules,
  relation types, allowed context pairs and purpose policies, registered as
  data. Imports `domain` and the standard library only.
- **`composition/`** — the only place where these layers are joined. Loads
  packs lazily through the allowlist and never at module scope.
- **`presentation/`** — exposure only through the existing MCP registry
  (ADR 0010) and the HTTP API, always through `composition`.
- New modules go into a concern package in every layer (ADR 0008). The
  existing `test/architecture/` tests enforce these rules. Implementing tickets
  add architecture tests for Project Intelligence.

### 10. Project contexts

Kernector keeps seven **logically separated but connected** project contexts.

- **A context classifies evidence. It is not a separate store, index or
  memory.** All contexts share the same catalog, relationship tables and
  retrieval path. A context does not classify people.
- **One artifact may belong to several contexts.** For example, an ADR is
  `documentation` and `backend`, and `openapi.yaml` in a service repository is
  `api_contract` and `backend`.
- **The vocabulary is registered data, not core literals.** The Software
  Delivery pack registers the seven contexts below and their default
  classification rules as data.
- **When no vocabulary is registered** (the pack is disabled), associations are
  valid with zero contexts and only context-free purposes, such as `answer`,
  run. A purpose that needs contexts reports that it is unavailable and never
  guesses.
- **Approved decisions are not a context.** They come from [#331] in their own
  bundle section.

| Context | Typical sources | Evidence it provides |
|---|---|---|
| `business` | Stories, bugs and requirements (Jira, GitHub issues) | Intended behaviour, acceptance criteria, defects |
| `api_contract` | OpenAPI 3.x and Swagger 2.0 files | Interface behaviour: operations, parameters, responses |
| `frontend` | Web and mobile UI code: components, routes and pages, state management, UI conventions | Implemented UI behaviour, structure and conventions |
| `backend` | Services, domain logic, persistence models, integrations, backend architecture notes | Implemented service behaviour, structure and conventions |
| `operations` | CI/CD pipelines, container and deployment descriptors, infrastructure as code, environment configuration (variable names only, never secret values) | How the project is built, deployed and configured |
| `testing` | Manual test cases (for example Xray Tests), automation code, reusable keywords, steps and fixtures | Existing coverage, framework conventions, reusable components |
| `documentation` | Confluence pages (once a connector exists), Drive documents, repository `docs/`, ADRs, written project conventions | Explanatory behaviour, rationale and conventions |

#### 10.1 Classification

- The association's context roles give each of its artifacts **default
  contexts**.
- **Deterministic artifact rules**, supplied by the pack as data, may **add**
  contexts to a single artifact or **replace** its defaults. Examples:
  - a Jira Test issue in a `business` scope is `testing` (replace);
  - `openapi.yaml` in a `backend` repository is `api_contract` and `backend`
    (add);
  - `.github/workflows/*.yml` and `Dockerfile` in any repository are
    `operations` (replace);
  - in a monorepo, path rules map `web/` to `frontend` and `services/` to
    `backend` (replace).
- **Every assigned context records its own reason:** `role_default`, or the id
  of the rule that added it. An artifact with two contexts has two reasons.

#### 10.2 Cross-context relationships

A relationship may connect artifacts in different contexts only with evidence,
under the same origin tiers (decision 4). The pack registers the allowed
relation types for each context pair. The initial set is:

| Subject context | Object context | Relation types | Assertion |
|---|---|---|---|
| `business` | `testing` | `tested_by` | — |
| `testing` | `business` | `tests`, `automates` | `coverage_evidence` |
| `frontend`, `backend` | `business` | `implements` | `implementation_evidence` |
| `backend` | `api_contract` | `implements` | `implementation_evidence` |
| `business`, `frontend`, `backend`, `operations` | `api_contract` | `references` | `mention` |
| `testing` | `api_contract`, `frontend`, `backend` | `exercises` | `coverage_evidence` |
| `documentation` | any | `describes` | — |
| any | any | `mentions` | `mention` |

`tests` and `tested_by` are inverses. An edge is stored once, in the outward
direction of the provider link type or rule that declares it, for example
`OIE-140 tests OIE-123` for a Jira "tests" link. Traversal follows both
directions and may show the inverse name, so `OIE-123` lists
`tested_by OIE-140`. Relations within one context, such as provider-declared
`blocks` or `duplicates`, need no pair rule.

#### 10.3 Task-aware selection

- Each consumer **purpose** declares one or more **evidence roles** per
  context. Packs register these policies as data. The core assembler hardcodes
  no purpose.
- Evidence roles are opaque policy tokens. The initial set is `behaviour`
  (intended or specified behaviour), `implementation` (what is currently
  built), `coverage`, `conventions`, and the reserved `excluded`.
- A purpose may label relation types with an **assertion**, for example
  `implementation_evidence` or `mention`. A file that merely mentions a story
  is never presented as proof that the story is implemented.
- **Test design and test generation** take `behaviour` only from `business`,
  `api_contract`, `frontend`, `backend` and `documentation`. `testing`
  supplies only `coverage` and `conventions`.

The initial policies the pack registers for those two purposes:

| Context | `test_design` | `test_generation` |
|---|---|---|
| `business` | `behaviour` | `behaviour` |
| `api_contract` | `behaviour` | `behaviour` |
| `frontend` | `behaviour`, `implementation` | `behaviour`, `implementation` |
| `backend` | `behaviour`, `implementation` | `behaviour`, `implementation` |
| `documentation` | `behaviour`, `conventions` | `behaviour`, `conventions` |
| `testing` | `coverage`, `conventions` | `coverage`, `conventions` |
| `operations` | `excluded` | `conventions` |

The context-free `answer` purpose declares no evidence roles and works with or
without a registered vocabulary.

#### 10.4 Conflicts

- When current evidence from different sources makes incompatible claims,
  Kernector reports a **conflict that cites every side**: source reference,
  revision and locator.
- It **never resolves a conflict silently** and **never ranks one context above
  another automatically**.
- Only two things resolve a conflict: an explicit user choice, or an approved
  [#331] decision that **cites the conflicting sources**.
- The assembler ([#377]) detects structural conflicts. The shared detector
  ([#389]) detects semantic conflicts for any purpose, so no consumer owns
  them.

#### 10.5 Outcomes

Every result reports each context with exactly one outcome:

| Outcome | Meaning |
|---|---|
| `available` | Current, relevant evidence was found and is included. |
| `empty` | The context is associated and synced, but nothing relevant matched. |
| `not_associated` | No confirmed association provides this context for the project or component. |
| `unsupported` | A source exists, but its format cannot be parsed safely, so it contributes nothing. |
| `stale_only` | The only matching evidence is `stale`. It is included with that label and never presented as current. |

Consumers report these outcomes instead of filling gaps with invented
evidence.

#### 10.6 Contexts, purposes and user roles stay separate

- A **context** classifies evidence. `testing` means existing-test evidence,
  not the QA role.
- A **purpose** names a task, not a persona.
- **User roles and permissions** decide only whether a caller may read a
  project or invoke a capability. Today that is the workspace binding and MCP
  allowlists; later it is [EPIC #257] membership and [#331] project
  permissions. They never choose contexts, evidence roles or selection
  policies, and no policy is keyed by a role name.

#### 10.7 Derived project views are reads, not stores

- Pack-owned derived views over current evidence, such as the technology
  profile ([#387]), are **computed on demand, per component**, like context
  bundles. They are never persisted as project state.
- They are delivered as **derived sections of the single context bundle**
  ([#377]), so consumers get one bundle.
- If a team wants a view to be authoritative, for example a project
  convention, it becomes an approved [#331] `project_convention` item. No other
  memory store is added.

### 11. Components

- A project has one or more **components**: separately deployed or owned
  units such as a web app, a service, or a test suite.
- A component is `component_id` + `name` + members. Each member is a confirmed
  association scope plus an optional path prefix, for monorepos.
- Each confirmed repository association gets a **default component** (reason
  `association_default`) **only if the operator has not assigned it to another
  component**. An operator's assignment is kept, and later syncs never
  overwrite it.
- Components have **no type field**. A component's contexts are **derived from
  its artifacts' classifications**.
- **Component dependencies are not stored.** They are aggregated at read time
  from current relationships whose ends are in different components.

### 12. Project Awareness

**Project Awareness** is what Kernector can currently show about a project,
with evidence: identity, components, contexts, relationships, technology
profiles, approved decisions, and their uncertainty.

- It is always **as of** specific source revisions and sync times. It **never
  claims completeness**.
- Every bundle reports, per context and per association, when the evidence was
  last synced and whether that sync succeeded.
- Absences are reported as outcomes (decision 10.5), not as facts.

Layers, from sources to consumers:

```text
connected sources            #287, #388
  -> project identity and components            #372
  -> normalized, classified evidence            #373
  -> relationships                              #374, #375, #376, #379
  -> awareness assembly                         #377 (with #387, #389)
  -> task-specific consumers                    #378, #368, #163, MCP clients
```

Approved decisions stay in [#331], and history stays in [#344].

## Rejected alternatives

| Option | Pros | Cons | Verdict |
|---|---|---|---|
| Relational tables in the existing SQLite database | No new infrastructure. Reuses the migration runner, workspace scoping and compare-and-swap. 1–2 hop joins are cheap at the expected scale (thousands to low hundreds of thousands of edges per workspace). Tests run offline. | Deep traversals need recursive queries. SQLite is single-writer until [#270]/[#271]. | **Selected** |
| Dedicated graph database (Neo4j or similar) | Native traversal and graph algorithms. | New operational dependency, auth surface, backup and migration. Duplicates workspace isolation. The query patterns do not need deep traversal. | Rejected for now |
| Hybrid retrieval with on-demand resolution only (no persisted edges) | No new storage. | Cannot keep provider links, human confirmations or invalidation state. Recomputes on every request. No audit. | Rejected as the sole approach. **Used** for retrieval-time traversal over persisted edges (decision 7). |

**Revisit triggers.** Reopen the storage decision if any of these happens:

- a verified use case needs traversal deeper than 2 hops;
- a workspace holds more than 1M relationships;
- p95 context assembly exceeds 500 ms on the evaluation fixture ([#371]) at
  10× scale.

## Consequences

- [#331], [#337] and [#344] reference `workspace_id + project_id` as defined
  here.
- Child tickets [#372]–[#379] build on these contract names and do not add
  their own stores or vocabularies.
- The core gains generic project, artifact and relationship contracts, but no
  Software Delivery literal. Disabling the pack leaves context-free features
  working.
- Inferred relationships always need a human to become evidence, so recall
  from inference grows only as fast as people confirm candidates.
- Storage stays inside SQLite. The revisit triggers above decide when that
  stops being enough.
- This ADR adds no code, migration or schema. The implementing tickets add the
  architecture tests that pin these rules.

## End-to-end example

Workspace `acme` holds project `oie` (`project_id` `prj_7f…`) with four
confirmed associations:

| Connector | Scope | Context roles | Component |
|---|---|---|---|
| Jira | `project_key=OIE` | `business` | — |
| GitHub | `repo=acme/oie-web` | `frontend` | `oie-web` (default) |
| GitHub | `repo=acme/oie-orders` | `backend`, `api_contract` | `oie-orders` (default) |
| GitHub | `repo=acme/oie-tests` | `testing` | `oie-tests` (default) |

Each repository is its own default component (reason `association_default`).

The relationship `OIE-140 —tests→ OIE-123` has:

- origin `provider_declared`;
- verification state `verified`;
- freshness `current`;
- confidence 1;
- evidence `jira:OIE-140@2026-10-01T10:00Z field=issuelinks`.

`OIE-140` is a Jira Test issue in the `business` scope, so a pack rule
classifies it as `testing` (reason: that rule's id). `OIE-123` is `business`
(reason `role_default`). The edge is therefore a `testing → business` `tests`
relationship, which decision 10.2 allows.
