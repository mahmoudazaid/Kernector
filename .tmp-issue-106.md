TITLE: Evaluate the RAG Pipeline with LLM-as-a-Judge

## Epic

#74 Quality / Evaluation

## User story

As an evaluator, I want an LLM-as-a-Judge evaluation of the RAG pipeline against a fixed dataset and explicit rubrics so I can measure context relevance, faithfulness/groundedness, answer correctness, and citation quality with reproducible evidence—treating judge scores as metrics, not ground truth.

## Rationale

Sprint 2 requires evaluation depth beyond a generic harness. A separate judge story makes RAG quality measurable, comparable across runs, and honest about judge limitations, without conflating automated scores with human truth.

## Exact scope

- Fixed evaluation datasets:
  - A **multi-source core** dataset (generic Kernector retrieval/answer quality across source kinds)
  - A separate **Software Delivery pack** slice (optional pack workflows; not the sole platform dataset)
- Rubric-based LLM-as-a-Judge scoring for:
  - Context relevance (including **cross-source** context relevance)
  - Faithfulness / groundedness
  - Answer correctness
  - Citation accuracy
  - Citation completeness / **source coverage**
- Baseline pass/fail thresholds per metric and/or aggregate gate
- Per-query evidence (scores + short explanations; retrieved context / answer / citations referenced)
- Aggregate metrics (means, pass rates)
- Failure categorisation distinguishing at least: unsupported claims vs retrieval failures vs generation failures, plus **per-source-kind** failure categories where useful
- Deterministic evaluation settings where the judge/provider supports them (e.g. temperature 0 / seed when available)
- Regression comparison against a stored baseline run
- Human review of a sample of cases (documented checklist or sampled IDs)
- Document judge model, version/id, prompt(s), settings, and limitations
- Implementation based on [RAGAS metrics](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/) and/or [LangSmith RAG evaluation](https://docs.smith.langchain.com/evaluation/tutorials/rag)

## Exclusions

- Treating judge verdicts as ground truth or sole acceptance of product quality
- Showing the judge expected numeric scores, target thresholds, or “correct grade” hints for the case under evaluation
- Asking the judge to evaluate or score its own hidden reasoning / private chain-of-thought
- Replacing human review entirely
- Full production observability platform setup beyond this evaluation command/report
- Expanding tool-calling eval beyond what is needed to exercise the RAG answer path (tool-specific eval remains owned by #102 unless extended here later)
- Treating Story Intelligence as the only evaluation domain

## Judge integrity constraints (mandatory)

- The judge **must not** receive expected scores, target thresholds, or “correct grade” hints for the case under evaluation
- The judge **must not** evaluate or score its own hidden reasoning / private chain-of-thought; only the visible answer, citations, and provided retrieved context (plus dataset fields allowed for the metric)
- Judge output is a **metric signal** used for dashboards, gates, and triage—not authoritative ground truth

## Acceptance criteria

- **Given** the fixed evaluation datasets and a RAG configuration, **when** the evaluation command runs, **then** it produces reproducible JSON and/or CSV results with per-case scores and explanations for context relevance, faithfulness/groundedness, answer correctness, citation accuracy, and citation completeness
- **Given** those per-case results, **when** the run finishes, **then** the output includes summary averages (or equivalent aggregates) and pass/fail against documented baseline thresholds
- **Given** failed or low-scoring cases, **when** results are inspected, **then** unsupported claims and retrieval-versus-generation failures are categorised (not only a single opaque score), including per-source failure labels where applicable
- **Given** cross-source cases, **when** judged, **then** cross-source context relevance and citation/source coverage are reported
- **Given** a baseline from a previous accepted run, **when** a new run regresses below thresholds, **then** the evaluation command exits non-zero
- **Given** the evaluation docs/report, **when** read, **then** judge model/version (or model id), prompt identity/version, settings (including deterministic settings where supported), and limitations are documented
- **Given** the judge prompts/inputs, **when** audited, **then** they do not include expected scores and do not ask the judge to evaluate its own hidden reasoning
- **Given** a documented sample of cases, **when** human review is performed, **then** review notes (or a completed sample checklist) are recorded alongside the automated metrics

## Technical notes

- Prefer composing on RAGAS and/or LangSmith RAG evaluation patterns rather than inventing a one-off opaque scorer
- Reuse the harness entrypoint from #102 where practical; this story owns the judge metrics, thresholds, regression gate, and integrity constraints
- Keep evaluation orchestration in application/infra boundaries consistent with Sprint 2 architecture (no Streamlit-owned scoring logic)
- Offline/fake mode or loud skip when credentials are missing is acceptable for local/CI without secrets, but the primary path must support a real judge run
- Store baseline artifact in-repo or under a documented path for regression comparison
